## 1. Kurz: Was die Applikation heute ist

Zwei Schichten:

1. **.NET-API** (`src/HotelChatbot.Api`) – RAG-Empfehlungspipeline über PostgreSQL/pgvector, Admin-UI, Crawling.
2. **Node-MCP-Bridge** (`chatgpt/index.js`) – Express-Server, den ChatGPT anspricht. Produktiv unter `https://mcp.bestalpine2.ms.mynet.at`.

Aktuelle MCP-Tools:

| Tool | Zweck heute | Problem |
|------|-------------|---------|
| `get_response` | Suche/Empfehlung via `POST /api/chat/recommend` | Nur Freitext `message`; keine Hotel-IDs in der Antwort; JSON-als-Text inkl. `_instruction` |
| `get_hotel_details` | Soll Detailfragen zu einem Hotel beantworten | Erwartet `hotelId`, die Suche liefert keine; ruft nicht existierendes `POST /api/chat` auf |

Transport heute: Custom JSON-RPC auf `/sse`, Protokoll `2024-11-05`.  
**Kein** `/mcp`, **kein** Streamable HTTP, **kein** offizielles MCP-SDK.

Weitere bekannte Lücken laut OpenAI:

- `GET /mcp` → 404  
- `GET /.well-known/openai-apps-challenge` → 404  
- `GET /health` gibt interne URL (`apiBaseUrl`, oft `http://127.0.0.1:8080`) aus  
- Keine Tool-Annotations (`readOnlyHint` / `openWorldHint` / `destructiveHint`)  
- Quellen-Footer `[to be done]`  
- Latenz der Suche ~18 s gemeldet  
- Hotel-Entity hat derzeit nur `HotelId`, `Name`, `Domain` (+ Meta) – Ort/Region/Land, offizielle URL, redaktioneller Freigabe-Status fehlen als strukturierte Felder

## 2. Was OpenAI konkret verlangt (Checkliste)

### Transport & Endpunkte

- [ ] Stabiler öffentlicher HTTPS-Endpunkt: `https://mcp.bestalpine2.ms.mynet.at/mcp`
- [ ] Streamable HTTP: `POST`, `GET`, `DELETE`, `OPTIONS` auf `/mcp`
- [ ] `/sse` darf übergangsweise bleiben, ist aber **nicht** mehr der Einreichungsendpunkt
- [ ] Domain-Verifikation: `GET /.well-known/openai-apps-challenge` liefert **reinen Text** (Challenge-Token aus dem Portal)
- [ ] `GET /health` nur z. B. `{ "status": "ok" }` – keine internen URLs/Versionen/Infra-Details

### Tools (Version 1 = nur Lesen)

- [ ] Klare, nutzerorientierte Namen/Beschreibungen
- [ ] Annotations pro Tool:
  ```json
  {
    "readOnlyHint": true,
    "openWorldHint": false,
    "destructiveHint": false
  }
  ```
  plus kurze Begründung (für das Portal)
- [ ] Keine Buchungen, Angebotsanfragen, E-Mails, Zahlungen, Schreiboperationen
- [ ] Strukturierte Input-Schemas (Suche: Region, Reisedatum, Personen, Adults-only, Budget, Hunde, Wellness-Fokus, …)
- [ ] Strukturierte Outputs inkl. Output-Schemas; stabile Hotel-IDs + Name
- [ ] Keine `_instruction`, Debug-Felder, Tokens, internen IDs, Stacktraces in Tool-Antworten
- [ ] Ungültige Hotel-ID → verständliche, sichere Fehlermeldung

### Inhalte / Sicherheit

- [ ] Nur redaktionell freigegebene Informationen
- [ ] Preise, Verfügbarkeiten, Spa, Zimmer, Angebote **nicht raten**
- [ ] Pro Hotel mindestens: ID, Name, Ort, Region, Land, offizielle Hotel-URL, Quellen-URL, freigegebene Inhalte nach Kategorien, Status/Datum letzter redaktioneller Prüfung
- [ ] Leere/nicht freigegebene Felder explizit als „nicht verfügbar“
- [ ] Rate Limiting, Request-Timeouts, CORS nur so offen wie nötig
- [ ] Logging ohne Tokens/vollständige Prompts/unnötige Personendaten
- [ ] Öffentliches Debug (`/debug-last-call`) entfernen oder absichern

### Einreichungsunterlagen (Portal)

- [ ] Exakt **5 positive** und **3 negative** Testfälle
- [ ] Bei geschützter App: Demo-Login **ohne MFA** (wenn kein Auth: ausdrücklich „öffentlich ohne Login“)
- [ ] Listing: Name, Kurz-/Langbeschreibung, Entwicklername, Kategorie, Website, Support, Privacy Policy, Terms
- [ ] Domain Verify + Scan Tools gegen Produktions-`/mcp`
- [ ] Nach Freigabe durch OpenAI: **du** veröffentlichst das Plugin

## 3. Arbeitsteilung: Ich vs. Du

### Ich (Agent) übernehme

1. MCP auf aktuelles Streamable-HTTP (`/mcp`) umstellen (idealerweise offizielles `@modelcontextprotocol/sdk`).
2. Tools, Schemas, Annotations, strukturierte Antworten inkl. Hotel-IDs.
3. `get_hotel_details`-Backend reparieren bzw. neuen Read-only-Detail-Endpunkt in der .NET-API.
4. Suche: strukturierte Filterfelder; Pipeline so anbinden, dass IDs + Metadaten zurückkommen.
5. `_instruction`, Quellen-`[to be done]`, Debug-Leaks entfernen; Fehlerantworten bereinigen.
6. `/health`, `/.well-known/openai-apps-challenge` (konfigurierbar per Env/Datei), Rate Limit, Timeouts, CORS.
7. Latenz verbessern (Timeouts + sinnvolle Fehler; wo möglich Caching/kürzere Pipeline-Pfade).
8. Hotel-Metadaten-Modell erweitern (Ort/Region/Land/URLs/Review-Status) – **technische** Seite.
9. Lokale + Produktions-Smoke-Tests (MCP Inspector); Checkliste abarbeiten.
10. Entwurf: 5+3 Testfälle, Tool-Annotation-Justifications, Listing-Texte (zum Gegenlesen).
11. Deploy-Skript/Docs anpassen (`/mcp` als kanonischer Endpunkt).

### Du (Gerhard) übernimmst

1. Entscheidungen freigeben (Tool-Namen, Auth ja/nein, welche Filterfelder Pflicht sind).
2. Redaktion: Hotelstammdaten + freigegebene Inhalte pflegen/prüfen (Admin), damit Felder nicht leer bleiben.
3. Produktion deployen bzw. Deploy freigeben (`DEPLOY-PRODUCTION.ps1` / Serverzugang).
4. OpenAI-Organisation/Developer Verification im Platform Dashboard (falls noch nicht erledigt).
5. Im Einreichungsportal: Challenge-Token erzeugen → mir geben → Domain Verify klicken.
6. Scan Tools, Formularfelder, Testfälle eintragen, Submit for review.
7. Nach Approval: Plugin veröffentlichen (laut Projektleitung ausdrücklich deine Aufgabe).
8. Mit Projektleitung: Privacy Policy / Terms / Support-URL / Logo / Demo-Video-URL bereitstellen.
9. Falls Auth geplant: Demo-Account ohne MFA; Zugangsdaten **nicht** unverschlüsselt in Mails/Repos legen.

### Projektleitung / Marketing (kurz)

- Listing-Texte, Logo, Markenfreigabe, Privacy/Terms-URLs, Demo-Recording.
- Kommunikation mit OpenAI nach Submit.
- Bestätigung: Version 1 wirklich nur Lesen (keine Buchungs-Features).
